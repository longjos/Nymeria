# Contributing to Nymeria

Thanks for helping build Nymeria. This guide covers commit conventions, the PR
workflow, and how releases are cut.

## Commit Messages: Conventional Commits (Required)

All new commits must follow the [Conventional Commits](https://www.conventionalcommits.org/)
format. Release notes and version bumps are generated automatically from commit
messages by [git-cliff](https://git-cliff.org) (config in `cliff.toml`), so a
well-written summary line goes straight into the changelog.

```
type(scope)!: summary
```

- `type` — required, one of the types below.
- `(scope)` — optional, the area touched (`transport`, `station`, `map`, `store`, ...).
- `!` — optional, marks a breaking change (or add a `BREAKING CHANGE:` footer).
- `summary` — imperative, lowercase, no trailing period. Write it to read well
  in a changelog — it will be published verbatim.

| Type | Release-notes group | Version bump |
|------|--------------------|--------------|
| `feat` | Features | minor |
| `fix` | Bug Fixes | patch |
| `perf` | Performance | patch |
| `docs` | Documentation | patch |
| `refactor` | Refactoring | patch |
| `test` | Testing | patch |
| `ci`, `build`, `chore` | CI/Build | patch |
| any type with `!` or `BREAKING CHANGE:` | (its group) | major |

Commits that don't match a type land in the "Other" group. Merge commits and
wiki-submodule bumps are excluded from release notes entirely.

Examples:

```
feat(transport): add serial KISS flow control
fix(station): persist sources across restarts
fix(beacon)!: change smart-beacon config keys to camelCase
perf(parser): avoid re-scanning AX.25 address fields
docs: document Direwolf KISS TCP setup
test(aprs): add Mic-E destination-field decode cases
```

## Pull Requests

- Open PRs against `main`. No force-pushes to `main`.
- The `test` CI check must pass: frontend build, `go vet`, and `go test`.
- CODEOWNERS automatically requests review from @longjos on every PR.
- Keep one logical change per commit; backend + frontend for the same feature
  can be a single commit. Reference issue numbers (e.g. `fix(map): ... (#42)`).

## Development Basics

- **Requirements:** Go 1.25+, pnpm 10, Node 22.
- `make build` — builds the frontend (pnpm) then the Go binary (frontend must
  build first: `web/build/` is embedded via `go:embed`).
- `make test` — `go test ./...`; `make lint` — `go vet ./...`. Both must pass
  before every commit.
- Backend work is test-driven: write tests first (the APRS spec, APRS101.PDF,
  defines correctness). See `CLAUDE.md` for the full workflow.
- Run locally with `./nymeria --listen :9090` (port 8080 is often taken on dev
  machines).

## Releases

Releases are maintainer-triggered via the **Release** workflow:

- **Tag push** (`v*`) — builds binaries and drafts a GitHub release with notes
  generated by git-cliff for that tag.
- **Manual dispatch, `tag-release` mode** — git-cliff computes the next version
  from the commits since the last tag (feat → minor, fix → patch, breaking →
  major), tags HEAD, and drafts the release.
- **Manual dispatch, `dry-run` mode** (default) — builds artifacts and a
  release-notes preview, publishes nothing.

Drafts are polished and published by the maintainer. Since notes come straight
from commit summaries, write summaries that read well in a changelog.
